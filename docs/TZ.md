Версия 1.0 · 15.07.2026
Статус: согласовано по итогам проектной сессии, готово к разработке

---

## 1. Обзор продукта

**Что это.** PWA-приложение для игроков живых покерных турниров (МТТ) в РФ, Беларуси и на Кипре (с расширением географии без доработок). Три ценности для игрока: все расписания серий в одном месте, напоминания о турнирах и их изменениях, личная турнирная статистика.

**Почему PWA.** Обход ограничений сторов на гемблинг-тематику, единая кодовая база, Web Push (с оговоркой по iOS — см. §9.2), установка на главный экран.

**Бизнес-цели:**
1. Собрать и удержать базу турнирных игроков (данные: гео, ABI, активность).
2. Фаза 2 — монетизация: посадка игроков на отборы/сателлиты партнёрских клубов (B2B) и premium-подписка.
3. Фаза 3 — социальные механики и рынок долей.

**Аудитория.** Регулярные и полурегулярные игроки живых МТТ-серий (RPT, EAPT и др.) в игорных зонах РФ (Красная Поляна, Приморье, Янтарная, Сибирская Монета), Беларуси и на Кипре. Сейчас пользуются Telegram-каналами серий и личными Excel-таблицами.

## 3. Модуль «Расписание» (MVP)

### 3.1 Сущности и иерархия

**Площадка (Venue)** → **Серия (Series)** → **Турнир (Event)** → **Флайт (Flight)**.

**Venue:** название, город, страна, игорная зона (опц.), таймзона (IANA, обязательно), адрес, координаты (опц.), лого.

**Series:** организатор (справочник: RPT, EAPT и т.д.), площадка, даты начала/окончания, статус (`announced` → `schedule_published` → `running` → `finished` → `cancelled`), постер, ссылки на источники (сайт, Telegram-канал), описание. Серия в статусе `announced` (даты есть, сетки нет) — полноценный объект: на неё можно подписаться.

**Event:** серия, порядковый номер, название, дата/время старта (в таймзоне площадки), бай-ин + валюта (RUB/BYN/USD/EUR, расширяемо), гарантия (опц.), стартовые блайнды как в сетке (опц., `100/200/200`; полная структура — отдельно), тип игры (NLH/PLO/…), формат-теги (турбо, баунти, дипстек, сателлит…), стартовый стек, re-entry (кол-во/unlimited), поздняя регистрация до уровня N, статус (`scheduled`/`changed`/`cancelled`), заметки.

**Flight:** принадлежит Event; метка (Day 1A/1B/…), своя дата/время. У турнира без флайтов создаётся один неявный флайт = самому турниру (напоминания всегда вешаются на флайт — единая логика).

**Структура блайндов** — опциональная вложенная таблица Event: № уровня, SB/BB/анте, длительность, отметка перерывов, отметка конца поздней регистрации. Отсутствие структуры не блокирует публикацию турнира.

### 3.2 Версионирование изменений

Каждая правка опубликованных Series/Event/Flight фиксируется записью в журнале изменений: что, когда, старое → новое значение, кто изменил. Типы: перенос времени, отмена, изменение бай-ина/гарантии, добавление турнира/флайта, публикация сетки серии. Журнал — источник событий для системы уведомлений (§5.4).

### 3.3 Интерфейс (публичный, без логина)

- **Главная:** лента карточек ближайших/идущих серий (постер, даты, площадка, страна, кол-во турниров, до старта N дней).
- **Страница серии:** шапка + список турниров, сгруппированных по дням; фильтры внутри серии по типу/бай-ину.
- **Карточка турнира:** все атрибуты, флайты, структура блайндов (если есть), время в TZ площадки + локальное время пользователя («19:00 местное · 12:00 у вас»), кнопки «в закладки» / «добавить результат» (требуют логин).
- **Календарь:** месячная сетка серий.
- **Фильтры глобально:** страна/зона, организатор, диапазон бай-инов, тип игры, даты, теги.

## 4. Модуль «Аккаунты и авторизация» (MVP)

### 4.1 Правовой контур

Авторизация через иностранные сервисы (Telegram, Google, Apple) запрещена для российских ресурсов (406-ФЗ, с 01.12.2023). Разрешённые способы: Госуслуги, ЕБС, российские сервисы (VK ID и т.п.).

> **Решение обновлено (2026-07-26):** MVP = вход по email OTP **или** email+пароль с подтверждением ссылкой. JWT access-токены не используются — сессии server-side (httpOnly cookie). [задел] VK ID — возможное дополнение в фазе 2.

### 4.2 Механика входа

**OTP:** пользователь вводит email → бэкенд нормализует (lowercase + trim) и генерирует OTP (6 цифр, TTL 5 мин) → доставка через email-адаптер → ввод кода → создание/поиск пользователя → сессия.

**Password:** регистрация (email + пароль + согласие) → письмо со ссылкой подтверждения → `verify-email` → сессия. Далее вход email+пароль. Восстановление: forgot → письмо → reset (инвалидирует все сессии). OTP-only пользователь может задать пароль в профиле.

**Антифрод (обязательно):** rate limit на email (не чаще 1 кода / 60 сек, ≤5/сутки) и на IP; капча при повторных запросах OTP и на register/resend/forgot; лимит попыток ввода кода (5) и пароля (lockout). Защита от email-бомбинга — критична.

**Телефон** — необязательный контакт в профиле (фаза 3), не способ входа.

### 4.3 Гостевой режим и мягкая регистрация

Расписание полностью доступно без логина. Закладки гостя сохраняются локально (localStorage/IndexedDB); при регистрации автоматически переносятся в аккаунт. Логин обязателен для: серверных закладок и напоминаний, трекера, профиля.

### 4.4 Профиль

Никнейм, аватар, город (опц.), базовая валюта статистики, email (идентификатор входа, отображается в шапке профиля; смена email — TODO), настройки уведомлений и приватности. [задел] Поле для будущей привязки Telegram-бота (фаза 2, только уведомления — не вход).

## 5. Модуль «Избранное и напоминания» (MVP)

### 5.1 Два уровня закладок

- **Закладка на серию** — события: «опубликовано расписание», «серия стартует через 7 дней / завтра», изменения дат серии.
- **Закладка на турнир/флайт** — напоминания к старту конкретного флайта + уведомления об изменениях этого турнира.

### 5.2 Настраиваемые интервалы

Глобальные настройки по умолчанию в профиле (например: за 24 ч и за 2 ч) + переопределение на конкретной закладке. Пресеты: 15 мин / 1 ч / 2 ч / 6 ч / 24 ч / 48 ч, множественный выбор. Все расчёты — от времени флайта в таймзоне площадки.

### 5.3 Канал доставки MVP: Web Push

Стандарт VAPID, библиотека `pywebpush`, без Firebase. Подписка запрашивается контекстно (после первой закладки), не при входе на сайт. У пользователя может быть несколько push-подписок (телефон + десктоп). [задел] Фаза 2: Telegram-бот как второй канал, выбор каналов в настройках.

### 5.4 Уведомления об изменениях

При правке в админке опубликованного объекта, на который есть подписки, автоматически формируются уведомления: «Турнир #12 перенесён с 18:00 на 20:00», «Турнир отменён», «Гарантия изменена», «Опубликовано расписание серии X». Это ключевая ценность продукта — приоритет надёжности доставки.

### 5.5 Экран «Мои закладки»

Список подписок с ближайшими событиями, управление интервалами, история отправленных уведомлений (последние 30 дней).

## 6. Модуль «Трекер результатов» (MVP)

### 6.1 Охват

Только живые МТТ. Поле `entry_type` в записи — enum с единственным значением `live_mtt` в MVP. [задел] Расширение на онлайн/кэш — добавление значений enum, не переделка.

### 6.2 Ввод результата

**Путь 1 — из карточки турнира:** кнопка «Добавить результат» → экран формы (`/tracker/results/new`) с автозаполнением (серия, площадка, дата, бай-ин, валюта), запись связывается с Event (FK).

**Путь 2 — произвольный:** ручной ввод всех полей (турниры вне базы, исторические результаты) на том же экране.

**Путь 3 — из текущего турнира:** финиш live-сессии создаёт результат и копирует хронологию (`live_events` → `result_events`).

**Форма как live-экран:** блок «Вложено», кнопки ре-энтри/заметка, лента событий с временем, блок финиша (в призах / без призов, место, поле, выплата, профит).

**Поля записи:** дата; название/связь с Event; площадка/серия (текст или FK); бай-ин; валюта; **хронология событий** (`result_events`: вход, ре-энтри, заметки с `occurred_at`); **количество входов** выводится из money-событий (в агрегатах вложено = бай-ин × входы); выплата (0 если не в призах); занятое место (опц.); размер поля (опц.); `entry_type`. Поле `results.note` — legacy (миграция могла перенести текст в событие `note`). [задел] Поле `my_share_pct` (доля себя, %, default 100) — в схеме БД с MVP, в интерфейсе скрыто до фазы 3.

### 6.3 Статистика и валюты

Метрики: турниров сыграно, вложено, выиграно, профит, ROI = (выиграно − вложено)/вложено, ABI, ITM%. Фильтры: период, серия, площадка, страна, диапазон бай-инов.

**Мультивалютность:** запись хранится в валюте турнира; агрегаты пересчитываются в базовую валюту профиля по курсу ЦБ РФ/ЕЦБ **на дату турнира** (курсы кэшируются в БД ежедневной задачей worker'а).

**График накопительного профита** (по турнирам/по времени) + шеринг-карточка графика (генерация изображения с брендингом приложения — виральный канал).

### 6.4 Приватность

Все результаты приватны по умолчанию. [задел] Флаги публичности в схеме профиля (`results_visibility`: private / itm_only / full) — интерфейс в фазе 3.

## 7. Админка (MVP)

Раздел `/admin`, доступ по ролям: `admin` (всё), `editor` (контент). [задел] Роль `partner` — фаза 2.

**Состав:**
1. **Справочники:** страны, зоны, площадки, организаторы, валюты.
2. **Редактор серий/турниров/флайтов/структур** — ручной CRUD с валидацией.
3. **Импорт расписаний** — парсер-пайплайн (§8): загрузка файла → черновик → экран сверки (таблица «как распознано» с подсветкой сомнительных ячеек) → правка → публикация.
4. **Журнал изменений** — автоматический (§3.2), с превью уведомлений, которые уйдут подписчикам, и подтверждением отправки.
5. **Управление пользователями и ролями** — `/admin/users` (только `admin`): список, поиск, смена роли `user`/`editor`/`admin`. Env-суперадмины (`SUPERADMIN_EMAILS`) не понижаются через UI.
6. **Дашборд контента:** серии без сетки, устаревающие данные, статистика парсинга.

## 8. Парсер-пайплайн расписаний (MVP, внутри админки)

Двухступенчатая схема: **детерминированные парсеры по умолчанию, ИИ — фолбэк**. Цель — минимизация токенов и стоимости.

### 8.1 Поток

```
Файл (xlsx/csv/pdf/jpg/png)
  → детект типа файла и источника (организатора)
  → есть шаблонный парсер? ──да──> кодовый парсер → confidence
  │                                   │ ok            │ низкий / упал
  │нет                                ▼               ▼
  └──────────────────────────> ИИ-фолбэк (Anthropic API)
                                      │
                              Общая валидация (Pydantic + sanity-чеки)
                                      │
                              Черновик в админке → редактор → публикация
```

### 8.2 Реестр шаблонных парсеров

- Парсер = Python-класс с единым интерфейсом: `parse(file) -> ParseResult` (список турниров в общей Pydantic-схеме + confidence 0–1 + список нераспознанных строк).
- Парсеры пишутся **под источник** (у каждого организатора устойчивый формат): `apc_xlsx_v1`, `rpf_pdf_v1`, `rpt_structure_pdf_v1`, …; EAPT PDF — после образца. Реестр сопоставляет источник → парсер.
- Библиотеки: `openpyxl` (xlsx), `pdfplumber` (PDF с текстовым слоем). `pandas` не используется.
- Изображения (постеры) детерминированно не парсятся — сразу в ИИ-ступень (vision).

### 8.3 ИИ-фолбэк

Триггеры: нет парсера под источник; парсер упал; confidence < порога; валидация забраковала. Оптимизация: если кодовый парсер распознал часть, в ИИ отправляются **только нераспознанные строки/фрагменты**, не весь файл. Модель через Anthropic API, промпт «извлеки сетку в JSON по схеме», structured output по той же Pydantic-схеме.

### 8.4 Валидация (общая для обеих ступеней)

Даты турниров внутри дат серии; бай-ин — положительное число; время валидно; нет дублей номеров; валюта из справочника; флайты одного турнира не пересекаются по датам абсурдно. Ошибки → подсветка в экране сверки. **Публикация всегда через человека.**

### 8.5 Учёт и развитие

Лог по каждому импорту: путь (код/ИИ/смешанный), токены и стоимость фолбэка, доля правок редактора. По логу видно, под какие источники выгодно написать шаблонный парсер. JSON-результаты ИИ по новому источнику сохраняются как тест-фикстуры для будущего кодового парсера.

## 9. Нефункциональные требования

### 9.1 Законодательство

- **152-ФЗ:** email = ПДн → БД и бэкапы физически в РФ; уведомление Роскомнадзора об обработке ПДн; политика конфиденциальности и согласие на обработку при регистрации.
- Приложение — информационный сервис; формулировки промо-материалов (фаза 2, отборы) проверять на соответствие рекламному законодательству.

### 9.2 PWA

- Манифест, установка на главный экран, иконки, сплэш.
- Сервис-воркер: кэш оболочки + оффлайн-доступ к ранее просмотренному расписанию и своим закладкам/статистике (stale-while-revalidate).
- **iOS:** Web Push работает только после добавления на главный экран (iOS ≥ 16.4) → обязательный онбординг-экран с инструкцией установки, показываемый iOS-пользователям при попытке включить напоминания.
- Известное ограничение SPA: нет SSR → слабое SEO публичных страниц. Принято осознанно; при необходимости — точечный пререндер публичных роутов позже.

### 9.3 Безопасность и производительность

- HTTPS всюду (Caddy, авто-TLS); httpOnly/secure cookie; CSRF-защита; rate limiting на auth-эндпоинты.
- Роли и проверка прав на каждом admin-эндпоинте.
- Целевые показатели MVP: до 10 тыс. пользователей, до 5 тыс. push-уведомлений/час; ответ API p95 < 300 мс.
- Ежедневные бэкапы Postgres (хранение в РФ).

## 10. Архитектура и стек

```
[Vite + React SPA (PWA)] ──REST──> [FastAPI] ──> [PostgreSQL]
                                       │
                    [Worker: APScheduler + pywebpush] ──> Web Push
                                       │
                              [Anthropic API] (парсер-фолбэк)
                                       │
                              [Email/SMTP] (OTP-код)
```

**Фронтенд:** Vite + React + TypeScript + Tailwind CSS; React Router; TanStack Query (серверное состояние/кэш); vite-plugin-pwa (SW, манифест, push); Recharts или аналог для графиков.

**Бэкенд:** Python 3.12 + FastAPI; SQLAlchemy 2.0 + Alembic (миграции); Pydantic v2 (схемы API и парсеров); авторизация OTP + сессии.

**Worker (отдельный процесс):** APScheduler; каждую минуту выборка «дозревших» напоминаний из очереди (таблица `notification_queue` в Postgres, статусы pending/sent/failed, ретраи); отправка через pywebpush; ежедневная задача обновления курсов валют. Redis/BullMQ не используются — масштаб не требует.

**Инфраструктура:** монорепо (`/frontend`, `/backend`, `/worker`); Docker Compose: `frontend` (статика за Caddy), `backend`, `worker`, `postgres`, `caddy`; VPS в РФ (Selectel/Timeweb/Yandex Cloud), ~от 1000–1500 ₽/мес; CI — сборка образов и деплой по push в main (GitHub Actions + деплой-скрипт).

## 14. План разработки (нарезка под ИИ-инструменты)

Разработка соло с Claude Code. Принцип: каждый этап — самостоятельный работающий инкремент; схема БД и Pydantic-схемы пишутся первыми и служат «контрактом» для генерации остального кода.

| # | Этап | Содержание | Критерий готовности |
|---|---|---|---|
| 0 | Каркас | Монорепо, Docker Compose, FastAPI hello, Vite+React hello, CI | Стек поднимается одной командой |
| 1 | Модель данных | Все таблицы §11 (SQLAlchemy + Alembic), сиды справочников | Миграции применяются, сиды на месте |
| 2 | Расписание read-only | API серий/турниров + публичные экраны (лента, серия, карточка, календарь, фильтры) | Вбитая вручную серия видна во всех экранах |
| 3 | Админка: ручной CRUD | Справочники, редактор серий/турниров/флайтов, роли | Редактор ведёт контент без разработчика |
| 4 | Авторизация | OTP по email, сессии, антифрод, профиль | Вход по email на проде |
| 5 | Закладки + push | Bookmarks, гостевые закладки + миграция, push-подписки, worker, напоминания и интервалы | Напоминание приходит в заданное время |
| 6 | Изменения → уведомления | change_log, генерация уведомлений при правках, экран «Мои закладки» | Перенос турнира → push подписчикам |
| 7 | Трекер | CRUD результатов, два пути ввода, статистика, курсы валют, график, шеринг-карточка | ROI/ABI считаются верно на тестовом наборе |
| 8 | Парсер-пайплайн | Инфраструктура импорта, 1–2 шаблонных парсера (по реальным файлам RPT/EAPT), ИИ-фолбэк, экран сверки, учёт токенов | Реальный файл серии → черновик → публикация |
| 9 | PWA-полировка | Манифест, SW, оффлайн-кэш, iOS-онбординг установки | Установка + оффлайн + push на iOS/Android |
| 10 | Запуск | Наполнение контентом (все актуальные серии РФ/BY/CY), бэкапы, мониторинг (Sentry/uptime), политика ПДн, уведомление РКН | Публичный релиз |

Рекомендация по работе с Claude Code: держать в репо файл `CLAUDE.md` с выжимкой этого ТЗ (стек, соглашения, структура БД) — он подхватывается как контекст в каждой сессии.

## 15. Риски

| Риск | Митигация |
|---|---|
| Устаревание расписаний → потеря доверия | Редакторский процесс + дашборд свежести (§7.5); парсер-пайплайн снижает трудоёмкость |
| Email-бомбинг / расходы на доставку | Антифрод §4.2, SPF/DKIM/DMARC на домене отправки, алерты на аномальный расход |
| iOS-пользователи без установки PWA → нет push | Онбординг §9.2; фаза 2 — Telegram-бот как канал доставки |
| Холодный старт аудитории | Шеринг-карточки статистики, открытое расписание (ссылки в чатах игроков), партнёрства с сериями |
| Правовые изменения (авторизация, реклама гемблинга) | Мониторинг; архитектурно способы входа и промо-блоки изолированы |
| Соло-разработка → bus factor | Монорепо, CLAUDE.md, миграции и сиды в коде, документированный деплой |
